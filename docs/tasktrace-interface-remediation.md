## Найденные первопричины

1. **Часы:** события responder использовали координаты цели события, а текст на веб-циферблате мог выделяться. Расчёт учитывал только один круг и отдельно AM/PM.
2. **Предварительный выбор:** открытие календаря сразу заполняло дату и время значением `now + 1 час`; видимый месяц не был отделён от выбранной даты.
3. **Готовность кеша:** snapshot-модели участников, overrides и авторов включали дополнительные `project_id`/`task_id`, которых нет в обычных RPC. Массивы без `id` сопоставлялись по позиции; изменившийся `is_read` сравнивался со старым значением. Покрытый кеш мог терять сертификат после обычного чтения.
4. **Участники:** переопределение собственной роли допускалось для владельца; ACL-перезагрузка сбрасывала загруженный экран и размонтировала окно. Повторное применение стартового кеша могло возвращать старые данные и офлайн-индикацию. На узком экране нулевой flex-basis имени оставлял слишком узкую колонку рядом с селектором; имя и управление теперь переносятся структурно.
5. **Обзор:** число этапов зависело от текущего списка `tasks`; для архивного проекта использовались также агрегаты архивного списка.
6. **Дедлайны:** компонент пункта располагался внутри условно раскрытых деталей; карточка пункта не использовала общий компонент анимации. Состояние дедлайна этапа вычислялось для цвета карточки, но соответствующая плашка не выводилась.
7. **Прочтение:** загрузчик мог применить старый список поверх подтверждённого изменения; `itemsRef` и видимое состояние обновлялись отдельно. Два запроса окна могли одновременно вернуть один ID с разными состояниями.
8. **Навигация:** `__TASKTRACE_INITIAL_PATH__` очищался только при восстановлении через `/projects`, оставался после прямого открытия ресурса и перехватывал первый возврат к списку.

## Технические решения и миграции

Существующие `deadlineState`/`deadlineSummary`, таймер границ дедлайнов, общий индикатор синхронизации, Realtime, read-model invalidation/CAS и `OfflineRuntimeProvider`/координатор сохранены. Второй механизм офлайн-подготовки не создавался. Проверка сертификатов продолжает проверять страницы, модели, assets, текущий день и ACL; прогресс не переводится в 100% искусственно. Отличаться от снимка могут изменяемые `is_read`/`is_completed`; признаки архива и блокировки доступа остаются строгими. Отдельный тест повреждённого `is_archived` подтверждает отказ в готовности.

У модели последнего автора идентичность задаёт `task_item_id`; смена самого автора не отменяет полноту данных. Для участников и получателей уведомлений `user_id` по-прежнему проверяется строго. После этого уточнения повторно прошли весь `npm test`, Web/Android/iOS export и браузерный сценарий восстановления Basic/Extended.

- `20261016153754_prevent_self_role_changes.sql`: добавляет проверку субъекта в `change_member_role`, `set_task_member_override`, `clear_task_member_override`; порядок блокировок и прочие проверки прав сохранены.
- `20261016154451_notification_filter_options.sql`: добавляет компактные варианты проектов/этапов для фильтров. Использует `SECURITY INVOKER`, RLS и явный `auth.uid()`; EXECUTE разрешён только authenticated. Новых таблиц и ослабления политик нет. Основа: [документация Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security).

Типы БД сгенерированы из мигрированной изолированной базы. Для целевого окружения требуется обычное применение обеих миграций перед публикацией соответствующей сборки.
