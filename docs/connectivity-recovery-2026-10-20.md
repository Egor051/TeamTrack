# Восстановление подключения TaskTrace — 20.10.2026

## Подтверждённые причины

- `connectivityFetch`, cache read и проверка пользователя сразу объявляли весь backend недоступным после транспортной ошибки отдельного запроса. Ошибка могла относиться к одному RPC, тайм-ауту или отменённому чтению. При этом источник данных из cache ошибочно подписывался как отсутствие интернета.
- Успешные ответы проверялись по connectivity epoch, ошибки — нет. Поздняя ошибка старого запроса могла закрыть уже восстановленный сетевой доступ.
- Проверка сервисов зависела от `auth.getSession()`, его refresh/cooldown и внутренних Promise. Тайм-аут HTTP fetch ограничивал получение заголовков, но не последующее чтение тела Auth-ответа. Зависшее тело могло удерживать SDK refresh даже после внешнего тайм-аута.
- AbortSignal без Promise race не гарантировал завершение UI query и probe, если адаптер игнорировал отмену. Чтение тела probe также оставалось без собственного предела.
- Автоматические проверки планировались только для `degraded`; состояние физического отключения и отрицательный `navigator.onLine` могли закрыть путь к проверке. Пропущенное событие online не всегда исправляло состояние.
- Refresh блокировался обычным `loading`, ждал активный pipeline до новой проверки связи и мог ждать старую операцию до её общего watchdog. Недоступный backend и физическое отключение показывались одним статусом «офлайн».

## Исправления и границы ответственности

`runtime-state.ts` остаётся владельцем сетевых фактов и живых операций; `coordinator.ts` сохраняет сериализацию sync/preload. Новый provider, outbox или цикл синхронизации не добавлялся. Используется существующий монитор доступности.

Ошибка отдельного запроса запускает одну общую подтверждающую проверку через 250 мс. Cache fallback относится к этому запросу. Ошибки RPC/SQL и HTTP 401/403 не превращаются в отсутствие интернета. Нормальное выполнение без установленного монитора сохраняет защитное закрытие сетевого пути при транспортной ошибке.

Проверка обращается к Auth health и Data API независимо от SDK refresh. Сохранённый JWT используется только для запроса; получение сохранённой сессии ограничено одной секундой, затем проверка может продолжиться без неё. Auth health проверяется без пользовательского JWT. Валидные JSON-ответы об отказе в авторизации показывают отдельную проблему авторизации; HTML/200 не считается успешным ответом сервиса.

Пределы:

- Auth token refresh/GET: 5 секунд на заголовки и тело ответа; фактические 401/403 сохраняются даже при зависшем теле.
- UI query: 5 секунд с отменой и Promise race.
- Каждый запрос probe вместе с JSON: 5 секунд; весь probe: 12 секунд.
- Чтение SDK session: 40 секунд; ошибка блокировки/SDK не объявляется отключением интернета и не удаляет сохранённые данные.
- Автоматическое восстановление после отказа сервиса: 30/60/120 секунд, без параллельных probe. Явный Refresh сбрасывает только connectivity backoff.
- При отрицательной подсказке браузера: редкая проверка сервисов через 120 секунд. Обычная офлайн-навигация использует локальные данные. Явный Refresh может проверить сервисы сразу.

Online/focus/pageshow/visibility и native foreground используют существующие подписки. Возврат физического подключения снимает старое ожидание и запускает свежую проверку. Короткий cooldown планирует оставшуюся секунду, а не оставляет длинный таймер офлайна. Поздние ответы и ошибки ограничены поколением проверки и request epoch.

Refresh доступен во время обычного чтения страницы. Он сначала проверяет связь, затем присоединяется к работе. Завершённые шаги обновляют время активности; длинный preload продолжает выполняться. При отсутствии прогресса 30 секунд старые tickets отменяются, после чего выполняется новое планирование. У bootstrap отмена ожидает нормальное освобождение lease/lock с ограниченным временем.

Формат IndexedDB/SQLite, протокол и ID операций, серверные receipts, разрешения, Basic/Extended readiness и ручное разрешение failed/conflict операций сохранены. Миграции и production flags не изменялись.

- Web export и генерация Service Worker — PASS. Дополнительно `expo export --platform all --output-dir .expo/connectivity-native-export` — PASS для Web, Android и iOS; это проверка сборки, не устройств.
- Chromium mobile-descriptor PWA через `scripts/mobile-offline-browser-smoke.mjs` — PASS: IndexedDB, cached history/notifications, Basic/Extended, офлайн reload и reconnect; 0 API requests при офлайн-навигации, JS page errors отсутствовали. Оба целевых браузерных скрипта завершились с exit code 0 в общем disposable harness.

Воспроизведение целевых браузерных проверок:

```powershell
$env:TASKTRACE_MOBILE_BROWSER_ENGINES = 'chromium'
node scripts/run-security-integrations.mjs scripts/connectivity-recovery-browser-smoke.mjs scripts/mobile-offline-browser-smoke.mjs
```

Стенд создаёт одноразовую локальную БД и сервисы, собирает PWA с loopback API, затем удаляет стенд. Он не использует hosted-пользователей или данные приложения. Evidence сохраняется в `.expo/connectivity-recovery/` и `.expo/mobile-diagnostics/` и не входит в Git.

## Ограничения

Hosted Supabase проверен только read-only: Auth health ответил 200, Data API без пользовательского JWT — ожидаемым 401/42501, ожиданий DB locks не было; в доступных edge logs за последние 24 часа не было 5xx. Это проверка текущей доступности, а не воспроизведение пользовательского эпизода.

Полный authenticated offline сценарий WebKit остановился с `page.goto: WebKit encountered an internal error` при переходе на URL в отключённой сети, без JS page errors. Он не засчитан как PASS. Chromium/device descriptors не являются проверкой физических Android/iOS или установленной PWA. Физические устройства не проверялись.

На этапе реализации commit, push, deployment и изменения hosted/infrastructure не выполнялись. Commit и push выполняются отдельно по последующей явной команде пользователя.
