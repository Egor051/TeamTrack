## 2. Архитектура участников и прав

Используется существующая `task_members`; отдельная система ролей не создавалась. Добавлен признак `is_direct`, по умолчанию `false`. Старые строки остаются состоянием наследования/переопределения и не превращаются в самостоятельные разрешения.

Правило существующего `private.task_role_of`:

1. Если нет проектного членства и явного `is_direct`, доступа нет.
2. При доступе применяется `role_override`, иначе проектная роль.
3. Для прямого участия без обеих ролей безопасным резервом служит только просмотр. Штатное приглашение всегда требует явно выбранную роль.

`private.lock_task_role` использует то же правило под существующими блокировками. Очередь офлайн-изменений продолжает применять прежние RPC и протокол v2.

Роли этапа `admin/member/viewer` регулируют чек-лист. Локальный `admin` может управлять его пунктами, но не получает права администратора проекта: не редактирует сам этап, не приглашает участников и не назначает исполнителей. Эти действия сохраняют проверку проектного `owner/admin`. Самостоятельное изменение своей роли запрещено. Проектный администратор не меняет полномочия проектного владельца/других проектных администраторов.

Приглашение в этап создаёт/обновляет только его `task_members`. Проектное членство не меняется. Удаление прямого участия:

- Для пользователя без проектного членства удаляет доступ и его назначение исполнителем этого этапа.
- Для проектного участника сохраняет членство и возвращает наследование проектной роли.
- Очистка отдельной роли сохраняет прямое участие и возвращает наследование, если проектная роль существует.

Удаление участника из проекта сохраняет прежнюю серверную семантику полного отзыва его доступов и назначений в этом проекте.

RLS проектов и проектных участников не расширена. Пользователь только одного этапа получает минимальный контекст родителя — название, идентификатор и статус — через авторизованный RPC. Описание проекта и соседние этапы ему недоступны. Доступный этап появляется в «Моих этапах» даже без назначения исполнителем.

История и дневной прогресс этапа работают с этим контекстом. История включает события его участников и исполнителей, отобранные по конкретному этапу. Имена участников доступны через проверяемый RPC без раскрытия email.

Обновления продолжают использовать общий Broadcast и механизм инвалидации. Проектные изменения передаются в защищённые темы этапов; пользователю только этапа не требуется подписка на проектную тему. Серверные уведомления и дедлайны учитывают прямых участников.

В существующий набор `roles` офлайн-снимка добавлены контекст и участники; новые наборы данных и версия протокола не вводились. Новые модели включены в общие ACL/account fences и подтверждение кеша. Для старого офлайн-снимка контекст может быть получен из уже подтверждённых моделей проекта и этапа без записи нового подтверждения доступа. При новой ACL-инвалидации такое получение запрещено, пока исходные модели не подтверждены.

Повтор и отмена неотправленного изменения этапа больше не снимают блокировку кеша всего проекта на основании одного чтения этапа. Проектную блокировку снимает только контекст, в котором сервер подтвердил действительное проектное членство. Пользователь только этапа может отменить своё неотправленное изменение офлайн, сохраняя закрытым кеш проекта.

## 3. Исправленные ошибки

### Мерцание

Установленный RN Web удерживает закрываемый fade-портал около 250 мс и снимает его из активного стека после анимации, отключая события указателя раньше. Это оставляет промежуточный период несогласованности визуального слоя, событий и фокуса. Постоянно смонтированные скрытые `Modal` также создавали порталы в порядке монтирования, а не фактического открытия.

Кроме этого, одно подтверждение участников отображалось двумя условными экземплярами внутри и снаружи родителя. Изменение состояния родителя могло перенести всё ещё открытое подтверждение в другой экземпляр.

`ModalLayer` теперь монтирует только открытый слой и удаляет его атомарно; используется `animationType="none"`. Общий механизм фокуса и Escape RN Web сохранён. Подтверждение участников принадлежит одной панели. Исправление не основано на увеличении z-index.

### Ложная ошибка обновления

Кеш уже отличал отменённое из-за нового состояния чтение (`SupersededReadError`) от серверного отказа, но экран этапа обрабатывал его как обычную ошибку. В репозитории чек-листа сходная гонка после ACL/account-инвалидации ошибочно превращалась в `ResourceAccessDeniedError`. Кроме того, общий `Promise.all` делал сбой вспомогательного чтения причиной отказа всего обновления.

Теперь прерванное устаревшее чтение не публикует ошибку и не очищает актуальный этап. Реальный отказ RLS продолжает отзывать доступ. Ошибки исполнителей/участников/последних редакторов имеют отдельное сообщение; основные данные и уже загруженные вспомогательные значения сохраняются в своём пользовательском и маршрутном контексте.

Диагностика `taskReadStep` указывает шаг, код, тип и HTTP-статус ошибки. Строки данных, токены и внутренние подробности не включаются в сообщение интерфейса.

При сохранении названия/описания новая форма отправляет исходные значения полей. RPC сравнивает их под блокировкой: конкурентное изменение вызывает `PT409`. Черновик остаётся в форме; после обновления показаны серверные значения и требуется явное продолжение с черновиком. Изменение прогресса/статуса чек-листа не считается конфликтом названия и описания.

## 4. База данных

Создана одна атомарная миграция:

`supabase/migrations/20261017012113_independent_stage_membership.sql`

Она добавляет `is_direct`, расширяет существующие функции вычисления/блокировки роли, RLS чтения этапов, управление отдельными ролями, назначения, уведомления, Broadcast и проекцию офлайн-набора `roles`. Представление `checklist_overview` остаётся `security_invoker` и учитывает доступные пользователю этапы без открытия строки проекта.

Новые RPC: `get_task_project_context`, `list_task_participants`, `add_task_member_by_identifier`, `remove_task_member`, а также перегрузка `update_task` с исходными значениями полей. Публичное и анонимное выполнение новых RPC запрещено; вызывающий пользователь и полномочия проверяются на сервере. Поиск пользователя при приглашении использует существующий общий лимит попыток, включая отказы. Имеющиеся индексы `task_members` покрывают новые обращения.

Старый трёхаргументный `update_task` сохранён для совместимости. Проверку конкурентного сохранения использует новая форма через пятиаргументный RPC. Типы БД пересозданы из мигрированной изолированной базы.

Hosted Supabase и общая локальная БД не мигрировались и не сбрасывались. Миграция применялась только к временным изолированным базам проверок.

## 6. Готовность и действия перед развёртыванием

Реализация завершена локально, временных заглушек нет. Для production нужны:

1. Проверить историю миграций целевой БД и применить новую миграцию до обновления клиента.
2. Собрать клиент со штатной production-конфигурацией (`npm run build:web`), развернуть и убедиться в обновлении PWA/service worker. Для production нельзя использовать результат `scripts/build-deadline-browser.mjs`: эта тестовая сборка подключается к локальному API `127.0.0.1:55539`. Старые клиенты сохраняют совместимость RPC, но не используют новую проверку конкурентного редактирования.
3. В целевом окружении проверить добавление только в этап, недоступность соседнего этапа, отзыв доступа и его доставку через настоящий Realtime.
4. Выполнить приёмку на реальных Android/iOS, включая вложенные окна, офлайн-перезапуск и восстановление сети.

Применение миграции и развёртывание клиента в hosted окружении не выполнялись.
