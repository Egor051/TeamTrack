# Клиентские ошибки TaskTrace: диагностика и безопасное восстановление

Подготовлено 28.10.2026. Реализация локальная: миграция, Edge Function и новая версия приложения требуют отдельного разрешения на публикацию. Исторический эпизод Ивана нельзя считать доказанным воспроизведением конкретного дефекта без события с его устройства.

## Подтверждённые проблемы и исправления

1. `userMessage()` сворачивал определённые локальные отказы в «Операция не выполнена». Классификация теперь централизована в `src/lib/errors/operation-error.ts`, использует действующие проверки connectivity/доступа и сохраняет исходный объект/SQL-код. Новые доменные ошибки сохраняют `cause`; внешние исключения получают контекст через WeakMap, без изменения их идентичности. UI получает только доверенные сообщения.
2. Чтение могло успешно вернуть серверные строки после неудачной записи кеша. Следующее изменение отвергалось драйвером из-за отсутствия подтверждённой базы. Сценарий воспроизведён с реальным IndexedDB-драйвером. Теперь `performSupportedEdit()` может один раз вызвать `ChecklistLocalRepository.recoverItemSnapshot()`: существующее чтение принудительно обновляет и подтверждает durable-снимок. Показанная пользователю версия сохраняется; новая версия сервера означает конфликт, а не автоматическое перебазирование черновика.
3. Ошибка разбора снимка в callback IndexedDB теряла исходную причину при `tx.abort()`. Причина сохраняется, а отсутствующий/повреждённый снимок и заблокированная цепочка получают отдельные коды. Web, native и Node-драйверы используют одну проверку подтверждённой записи.
4. Для `42501` без HTTP `status` теперь применяется понятное сообщение о доступе. Ошибки сессии, квоты хранилища, транзакций, возможностей локальной записи и конфликта различаются.
5. Cache-first мог вернуть версию, прочитанную до замены снимка во время асинхронной фильтрации/проверки доступа, и признать её свежей по времени уже нового снимка. Отдельный тест сначала воспроизвёл возврат v2 вместо v3. Теперь существующий путь чтения сверяет исходные данные, включая обе части виртуального `all`, и повторяет локальное чтение не более трёх раз. При непрерывных изменениях срабатывает штатный `SupersededReadError`; сетевой цикл и перебазирование операции не добавляются.
6. Runtime-конфигурация копировала исключение через object spread и затем возвращала безопасный `unavailable`. Для настоящего `Error` такая копия теряла неэнумерируемые `message/cause`. Теперь сохраняется исходный объект с HTTP status, а ошибка публикуется до fallback вместе с эффективными capabilities. Ошибка сохранения tombstone также фиксируется, volatile-запрет остаётся обязательным. Это наблюдаемость существующей политики, без расширения прав.

Исправление не меняет роли, CAS, coupling checkbox/процента, протокол v3 или бизнес-outbox. Автоматического восстановления после неоднозначной ошибки записи, удаления очереди, сброса IndexedDB и автоматического выбора новой версии нет. При недоступной сети требуется сохранённая подтверждённая база и действующее разрешение офлайн-записи. Отказ `write_enabled` при накопленных операциях сохраняет прежнюю безопасную политику.

Граница безопасности не расширялась: выключенный sync означает эффективное `write=false`, даже если отдельный write-флаг true; сохранённая очередь остаётся на устройстве. При `write=false` и чистом пункте остаётся штатная online-операция, а наличие накопленной цепочки не позволяет перепрыгнуть через неё. Истёкшая сессия не получает новых офлайн-разрешений. Подтверждённые capabilities могут использоваться офлайн по существующей политике, transport-failure не подменяет отказ 401/403.

`pending` продолжает образовывать цепочку зависимостей; `failed/conflict` дают отдельное сообщение и сохраняются; review и подтверждённые, но ещё не согласованные операции используют прежние механизмы индикатора/receipts. Повтор потерянного ACK использует тот же UUID. Операции не удаляются ради восстановления снимка.

При медленном обновлении UI после ACK новый черновик может быть начат со старой видимой версией. CAS обязан сохранить эту версию и выдать конфликт, если сервер уже изменился. Это отдельно проверенное защитное поведение: успешный браузерный сценарий ожидает исчезновения «Ожидает синхронизации», а тесты устаревшего черновика продолжают запрещать автоматическое перебазирование. Конкретный участник, изменивший версию, по одному CAS-ответу не устанавливается.

Схема IndexedDB и протокол не повышались: открытие v5 с существующим fallback для установок v6, durable receipts и миграция формата остались прежними. Уничтожение данных, автоматическое исправление физически повреждённой БД и принудительное обновление всех старых PWA не реализовывались. Квота/ошибка транзакции показываются явно; при неоднозначном результате записи автоматический повтор запрещён. Физическое устройство с повреждением хранилища требует индивидуального расследования, а не общего reset.

## Архитектура

`userMessage`, ошибки кеша, локальное редактирование, sync и необработанные web-исключения → `reportClientError` → строгая проекция события → ограниченный диагностический буфер в существующем cache driver → `POST /functions/v1/client-errors` → проверка JWT через Auth `/auth/v1/user` → прямой PostgreSQL → `private.ingest_client_error` → `public.client_error_logs`.

Один транспорт — Edge Function. Он выбран из-за наблюдавшейся раздельной доступности Auth и Data API. Использование Edge с вызовом PostgREST не решило бы эту задачу, поэтому сервер обращается к PostgreSQL напрямую. Для него закреплён `postgres@3.4.9` в отдельном `deno.lock`; зависимость не входит в приложение. Потеря связи с Auth или самой БД всё равно делает доставку невозможной: функция возвращает безопасный отказ, приложение продолжает свою работу.

Функция сверяет пользователя на Auth-сервере при каждом фактическом приёме. API key сам по себе не является аутентификацией. `user_id` отсутствует в клиентском контракте и устанавливается исключительно по ответу Auth. Дополнительно проверяется наличие активного аккаунта в БД. Приватная ingest-функция недоступна `PUBLIC`, `anon`, `authenticated` и `service_role`; вызывать её может доверенное серверное подключение владельца.

Схема `supabase/functions/_shared/client-error-schema.ts` общая для frontend и Edge. PostgreSQL независимо проверяет те же допустимые поля, значения и размер. Любые лишние поля, включая вложенные, отклоняются.

Событие содержит UUID, время, версию приложения/build, протокол, доступную версию управляющего SW, тип операции и этап, классификацию/имя/код исключения, до трёх безопасных описаний причин, до шести координат известных модулей, connectivity и причину сетевого состояния, capabilities, состояние снимка, счётчики outbox и известные версии. Неизвестный тип/код заменяется `UnknownException`/`OTHER`. Безопасное описание генерирует сервер по категории.

Не передаются сообщения исключений, сырой stack, URL и query string, токены, пароли, HTTP headers, тела запросов, комментарии, имена проектов/пунктов, содержимое IndexedDB или бизнес-идентификаторы. JWT используется только в Authorization транспорта и не входит в событие/буфер. Координаты minified bundle сопоставляются с доверенным артефактом соответствующей сборки. Исходная цепочка исключений остаётся доступной локально через оригинальное исключение и `cause`.

Service Worker отвечает на локальное сообщение `TASKTRACE_SW_VERSION` идентификатором сборки, вычисленным из сгенерированного Workbox-кода до добавления обработчика версии. Старый worker может не поддерживать запрос: тогда версия `null`. Запрос ограничен 500 мс. Обновление по выбору пользователя, сохранение вводимых данных и действующий offline-shell остаются прежними; принудительный reload не добавлялся.

## Ограничения и доставка

| Ограничение | Клиент | Сервер |
|---|---|---|
| Только ошибки | Подписка на исключения/ошибки операций | Контракт не принимает activity/произвольные типы |
| Размер | UTF-8 `JSON.stringify(event)` ≤4096 байт | Edge считает фактически прочитанные bytes; SQL проверяет JSONB и полную сериализованную запись с серверными полями ≤4096 байт |
| Суточный лимит | До 20 новых событий и до 20 попыток HTTP на аккаунт/UTC-день, включая retry | До 20 сохранённых событий на пользователя/UTC-день |
| Дедупликация | Структурный fingerprint, 15 минут; также ограничены чтения метаданных | Event UUID и серверный fingerprint, 15 минут |
| Частота | Не чаще одной отправки в 30 секунд | Не чаще одной новой записи в 30 секунд, под пользовательской advisory-блокировкой |
| Повторы | Максимум две попытки на событие, следующая не раньше 60 секунд | Повтор UUID подтверждается без новой записи |
| Локальный буфер | Не более 10 событий, 48 КиБ вместе с ledger, TTL 48 часов | — |
| Время | Отправка ограничена 6 секундами | Handler 4,5 секунды; DB statement 2 секунды; lock 500 мс |
| Хранение | Истёкшие диагностические записи отбрасываются при чтении | Очистка записей старше 14 дней |

Буфер занимает один отдельный ключ `diagnostics:client-errors:v1` в существующем хранилище кеша. Он не является записью бизнес-outbox и не участвует в порядке пользовательских операций. После перезапуска неподтверждённое событие сохраняет UUID и счётчик попыток. Смена аккаунта прерывает доставку и не перепривязывает события к другому пользователю. Ошибка IndexedDB переводит диагностику в ограниченный буфер памяти текущего процесса; после закрытия такой вкладки его содержимое теряется.

Ошибки диагностического чтения/доставки не публикуют новые ошибки. Отправки запускаются событиями уже существующего lifecycle: ошибка, запуск, восстановление подключения, смена токена, возврат в foreground. Отдельных polling-таймеров нет. Пустой буфер не создаёт HTTP-запросов. Для диагностики допускается Edge-доставка при `degraded` Data API; физическое отсутствие сети сохраняет буфер. Истёкшая сохранённая сессия ожидает восстановления Auth без отправки токена в событии.

Клиентские лимиты при исправном хранилище общие для вкладок через существующий CAS. При недоступном хранилище действуют ограничения памяти каждого процесса, а серверная квота остаётся общей и обязательной. Гарантировать ноль запросов от модифицированного/злонамеренного клиента нельзя; сервер ограничивает сохраняемый объём и конкурирующие приёмы.

Одна дополнительная задача `tasktrace-client-error-retention` выполняется в `43 * * * *`, пакет ≤10000 строк, statement timeout 10 секунд, `SKIP LOCKED`. Существующие три задания не переписываются. При исправном Cron физический хвост между запусками может существовать до следующего часа; задержка/ошибка Cron видна в `cron.job_run_details`. При больших очередях очистки нужны контроль backlog и свободного места, без автоматического расширения тарифа или изменения production-настроек.

## Нагрузка и Supabase Free

При отсутствии ошибок дополнительных HTTP-запросов нет. Один запрос доставки вызывает один запрос проверки Auth и один SQL-запрос. CORS preflight может добавить OPTIONS; ответ разрешает кешировать preflight 24 часа. Никакого Realtime для таблицы нет.

Средний размер зависит от координат/цепочки причин. В сквозном наборе из 24 изолированных тестовых записей (включая fixtures квоты) измерены среднее 1199 байт и максимум 1212 байт; четыре клиентских HTTP POST доставили четыре реальные ошибки, 20 записей относились к проверке квоты. Это измерение примеров, не предсказание для всех исключений. Размеры/число запросов фиксирует `.expo/client-error-e2e-<pid>/results.json`. Номинальный бюджет за 14 полных UTC-дней: `20 × 14 × 4096 = 1 146 880 байт`, около 1,094 МиБ на пользователя. Скользящий интервал 14 суток пересекает до 15 UTC-дат: его строгий максимум — 300 записей, 1,172 МиБ. С часовым интервалом исправного Cron физическое хранение может пересечь до 16 UTC-дат: консервативно 320 записей, 1,25 МиБ на пользователя; 125 МиБ для 100 пользователей и около 1,22 ГиБ для 1000. Эти оценки предполагают отсутствие backlog очистки и учитывают только сериализованное содержимое: индексы, JSONB overhead, MVCC, WAL и остальная БД считаются дополнительно. Сам предел 20/сутки не гарантирует соответствия Free при любом числе пользователей.

Клиентский максимум 20 HTTP-попыток в день даёт `600 × N` вызовов за 30 дней при N ежедневно ошибающихся пользователей. Для 100 это до 60000, для 1000 — до 600000, плюс возможные preflight и прочие функции проекта. Нормальное потребление значительно ниже при редких ошибках и дедупликации. Перед включением сверить фактическую аудиторию/занятое место и общие квоты проекта: [Edge Function invocations](https://supabase.com/docs/guides/functions/pricing), [database/disk usage](https://supabase.com/docs/guides/platform/database-size), [актуальные планы](https://supabase.com/pricing). Документация на момент проверки указывает 500000 включённых Edge-вызовов для Free; квота общая, не резерв диагностики.

## Просмотр в Dashboard

SQL выполняет только доверенный оператор в SQL Editor. Примеры находятся в `docs/client-error-diagnostics-queries.sql`: последние ошибки, пользователь/период, распространённые причины, версия приложения, размер таблицы и состояние Cron. Обычным пользователям не выдаются политики SELECT/INSERT/UPDATE/DELETE; все логи доступны только административному контексту Dashboard/`service_role` с разрешением чтения.

Для расследования найти `user_id` в Auth Users, выбрать нужное время с явным UTC offset и рассмотреть `kind`, `stage`, `event.error.code`, безопасные причины, `network_issue`, capabilities, снимок, outbox и версии. Например, `TT_LOCAL_SNAPSHOT_MISSING` + `cache.snapshot=missing` локализует отказ базы операции; `outbox.failed>0` объясняет блокировку цепочки; `conflict` с разными версиями означает CAS-конфликт. Событие показывает состояние во время сбора, а не доказывает причину более раннего эпизода. Отсутствие события может означать отсутствие сети/Auth, выключенную диагностику, старый клиент, дедупликацию, квоту либо исчерпанные попытки.

## Безопасное внедрение: отдельные ручные действия

1. Получить разрешение на deployment. Проверить фактическую схему и историю. Новая миграция — **только** `20261028142906_client_error_diagnostics.sql`. Уже применённые миграции не запускать повторно; общий `db push --include-all` не использовать. Файл учтён как отдельный follow-up в release manifest и не добавлен к исторической шестишаговой цепочке.
2. После разрешения применить эту forward-миграцию. Она создаёт таблицу/индексы/приватные helpers и одну задачу Cron, не меняя бизнес-таблицы. При lock timeout остановиться и выбрать подходящий момент; не ослаблять ограничения.
3. Подготовить серверный `CLIENT_ERROR_DB_URL` для transaction pooler либо проверить managed `SUPABASE_DB_URL`. Это серверный секрет Edge; он не должен попадать в `.env` frontend, `EXPO_PUBLIC_*`, логи или команды с открытым паролем. Удалённое подключение принудительно использует TLS с `rejectUnauthorized=true`; если корень не входит в доверенные, скачать сертификат проекта в Database settings и задать его PEM в серверном `CLIENT_ERROR_DB_CA`. Проверка сертификата не отключается; plaintext разрешён только для loopback изолированных тестов. `max:1`, `max_pipeline:1`, `prepare:false`, `fetch_types:false` ограничивают соединения, исключают pipeline и служебное чтение типов. Настройки соответствуют [рекомендациям Supabase для serverless/Postgres.js](https://supabase.com/docs/guides/database/connecting-to-postgres#configure-your-client). Hosted TLS и доступ к pooler должны быть проверены оператором перед включением клиента.
4. При необходимости задать `CLIENT_ERROR_ALLOWED_ORIGINS` точным списком web-origin через запятую; default — `https://tasktrace.ru`. Для локальной проверки разрешать только свой loopback-origin. Origin не заменяет Auth. `verify_jwt=false` в конфигурации означает, что проверку выполняет handler через Auth `/user`; анонимный доступ при этом не разрешается.
5. После разрешения опубликовать `client-errors`, например `supabase functions deploy client-errors`. Секреты вводить через защищённые средства Dashboard. Убедиться в HTTP-отказе без пользовательского JWT, закрытых grants/RLS, отсутствии таблицы в Realtime и наличии активного Cron. Положительная production-canary пишет только заранее одобренное диагностическое событие.
6. Только после готовности backend собрать frontend с `EXPO_PUBLIC_CLIENT_DIAGNOSTICS_ENABLED=true`. По умолчанию/example значение `false`. Для native/CI рекомендован неизменяемый `EXPO_PUBLIC_APP_BUILD_ID` (7–64 lowercase hex); web дополнительно умеет определять hash entry-bundle. Использовать штатную сборку с очисткой transform cache, чтобы публичный API URL и флаги соответствовали артефакту.
7. После отдельного разрешения опубликовать приложение, проверить Android/iOS/PWA и контролируемое обновление SW. Включить наблюдение за числом событий, `pg_total_relation_size`, Cron и общими квотами. Отключение диагностического флага в следующей сборке останавливает новые события; бизнес-outbox не затрагивается.

Security gate больше не требует совпадения содержимого build/helper-файлов с историческими хешами. Изменение Service Worker или клиентского контракта меняет fingerprint текущих входов сборки, поэтому перед проверкой gate нужно заново собрать артефакты; ручное обновление security policy из-за одного лишь изменения файла не требуется. Gate по-прежнему проверяет фактические workflow permissions, pinning Actions, unsigned export, запрет signing/privileged inputs, свежие platform source maps и соответствие artifact hashes текущему checkout. Остаточные зависимости и условия их пересмотра описаны в постоянном реестре `scripts/security-policy.json` и отчёте [security-risk-register-2026-10-29.md](security-risk-register-2026-10-29.md).

Миграции/Edge/frontend в production этой задачей не применяются. Отдельного административного интерфейса в приложении нет. Новые логи не восстанавливают задним числом отсутствовавшую телеметрию Ивана.

## Воспроизведение локальных проверок

- `npm test` — действующие DB connection policy, typecheck, lint и все unit-тесты.
